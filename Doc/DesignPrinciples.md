# Jejune Design Principles

## Ecosystem Repository Resolution

Whenever a jejune component needs a sibling ecosystem repository, it uses a
three-tier resolution strategy that prioritises local availability:

1. **`JEJUNE_ROOT_DIR/<name>`** — a permanent local clone under the ecosystem
   root. Preferred for active development: changes take effect immediately
   without committing upstream.
2. **`.jejune/tmp/<name>`** — a temporary clone created on demand (e.g. by
   `jejune catalog test`). Lower priority than the root clone; the original
   remote URL is always recorded alongside the local path.
3. **`REPO_ROOT_DIR/<name>`** — fetched directly from the remote at the URL
   defined by `ecosystem-repo-base` in `jejune_cli/pyproject.toml`. Used as
   last resort when no local copy is present.

This ordering enables a development cycle where in-progress changes to one
ecosystem repository are visible to dependent components without requiring an
upstream commit or release, while still working out-of-the-box for users who
have not cloned the full ecosystem.

### Key constants

| Name | Where defined | Purpose |
|---|---|---|
| `REPO_ROOT_DIR` | `jejune_cli/jejune_cli/_ecosystem.py` (generated by build hook from `pyproject.toml`) | Base URL of the GitHub organisation hosting all ecosystem repos |
| `JEJUNE_ROOT_DIR` | environment variable | Local directory containing permanent clones of ecosystem repos |

`REPO_ROOT_DIR` is the single source of truth for the remote base URL. It is
defined once in `[tool.jejune] ecosystem-repo-base` in
`jejune_cli/pyproject.toml` and baked into `_ecosystem.py` at build time by
`hatch_build.py`. It is not overridable via environment variable.

### Implementation

The resolution logic lives in `jejune_cli/jejune_cli/ecosystem.py`:

- `repo_status(name, root_dir, tmp_dir)` — returns the resolution tier and
  resolved path or URL.
- `resolve(name, root_dir, tmp_dir, subpath)` — returns the string to pass as
  a Docker build context (absolute local path or git URL with `#main:<subpath>`
  fragment).

`jejune build` calls `resolve()` for each service image before invoking
`docker compose`, setting `DOCS_SERVER_CONTEXT`, `KG_GRAPH_VIEWER_CONTEXT`,
and `MARKDOWN_BROWSER_CONTEXT` in the subprocess environment.

### Visibility

Run `jejune ecosystem` from any directory to see which repos are resolved via
which tier for the active role.

## Role Inheritance

The "developer" role is a conceptual base role inherited by all other roles:

```text
developer
├── doc-steward
├── catalog-curator
└── deployer
       └── catalog-curator
```

This means `JEJUNE_ROOT_DIR` configuration and the `ecosystem` command are
visible regardless of the active role. No directory-level signal is needed to
activate developer features; they are always present.
